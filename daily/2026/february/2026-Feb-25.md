## On versioning

Current version is v0.3.6 where the first number indicates the major version, the second number indicates the minor version, and the third number indicates the patch version. This is a common versioning scheme but does not capture what I want to express with the version numbers.

I want to be able to indicate when a change is breaking, even if it's a minor change, and I also want to be able to indicate when a change is major, even if it's not breaking. For example, a major change could be a syntax overhaul that does not break backward compatibility, while a minor change could be a bug fix that does break backward compatibility.

I am thinking to switch to the following versioning scheme for Lyre:

- Major change counter: incremented each time a drastic language changes, such as syntax overhaul or paradigm shift
- Minor change counter: incremented each time bug fixes and optimizations and such happen, within the same language design
- Breaking counter version: incremented each time a major or minor change breaks backward compatibility.

We need to replace the current version to `3.6.0` first, and then we can start using the new versioning scheme from there. So the next version after `3.6.0` would be `4.0.0` if it's a major change, `3.7.0` if it's a minor change, and `3.6.1` if it's a breaking change. None of this numbers decrease, so we can always know how many major and minor changes have happened since the initial version, and how many breaking changes have happened in total.

We can also check if a specific version is compatible with another version by comparing the major and minor change counters, and checking if the breaking counter version is less than or equal to the other version's breaking counter version.
